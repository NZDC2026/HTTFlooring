## 代码回滚

本次没有改变运行中的系统。需要撤销本提交时，在工作区无其他未保存改动的前提下执行：

```sh
git revert <本次提交ID>
```

这会以一个新提交撤销本次新增/修改并把旧目录恢复为 `htt-backend`，保留提交历史。它不会移除父提交中已有的Java接口，也不会操作数据库、容器或真实服务。不要用强制重置覆盖后来产生的改动。

## 运行时回滚方式（仅供以后受控发布使用）

1. 停止接收相关新写入，停止Java后台任务并等待在途任务完成或原租约失效；保留一致性备份及已验证的原.NET镜像/配置。
2. 使用保留的 `htt-backend-c#` 版本恢复.NET API和Worker，继续使用受限的 `htt_app` / `htt_portal` / `htt_worker` 登录。API或Worker不得使用迁移所有者凭据。避免两套后台写入者重叠。
3. 检查存活/就绪、认证、队列状态、账务控制余额及待处理任务，再按已批准的发布流程恢复流量。这些生产步骤本次均未执行；本次演练仅在合成数据库内完成。
4. 001–055无需降级或重写。056只为不可变 `sales.order_lines.id` 增加行锁所需的列级UPDATE授权，原追加写保护触发器仍拒绝实际修改。回滚.NET时可保留该窄授权；两套实现的缺货处理均需要相应行锁。

如确需撤销056授权，应先保持相关缺货写入停止，由迁移所有者执行：

```sql
REVOKE UPDATE(id) ON sales.order_lines FROM htt_app;
```

恢复Java相关写入前，如此前撤销过授权，显式恢复：

```sql
GRANT UPDATE(id) ON sales.order_lines TO htt_app;
```

保留迁移历史及业务数据，不删除056历史记录来强迫重跑。单纯撤销授权不会清除历史记录，迁移工具因此不会自行再次授予它。无需删除表、回退业务数据或重置队列；若发生后来产生的数据问题，应单独评估备份恢复，不把代码回滚当作数据回滚。

含 `#` 的目录路径在Shell中始终加引号，例如 `cd 'htt-backend-c#'`。
