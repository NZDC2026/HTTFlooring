# Prevent reusing previously cleared bank movements

The imported statement workbench now excludes rows already cleared by manual or imported bank reconciliation. The main match command also rejects those row IDs, including IDs submitted from a stale candidate list. A new external bank line must use its genuine receipt, payment, transfer or categorisation source; an identical amount alone does not make an earlier cleared source reusable.

A shared ownership check rejects an imported line dated after the statement that already cleared its selected ledger row. Imported reconciliation and the underlying manual reconciliation command both enforce it before accepting a new result. The existing reconciliation-chain verifier applies the same rule during period close and interrupted-operation recovery. This also blocks positive/negative pairs whose net amount is zero: a zero closing difference cannot justify reusing two earlier cleared cash movements.

Legacy wrong matches remain loadable for diagnosis. An unreconciled MATCHED line may be unlinked without reversing its underlying source, releasing historical clearing or changing GL. The prior matched ledger IDs are retained in its Reverted history reason and the command remains under banking.write authority and security audit. The user can then record/select the genuine source, match and reconcile normally. A failure after unlink rolls back the whole command.

Completed statement lines remain locked. POSTED categorisation reversals still require uncleared source journals; the relaxation applies only to removing an unreconciled MATCHED association. The latest reconciliation cutoff, original GL, saved reconciliation records, journal/source locks and normal financial write gate remain in force. Already completed false historical reconciliation is detected by close/recovery checks but is not automatically rewritten or unlocked; it requires the existing validated backup/reviewed recovery route.

No independent backend or external bank call is added. The persisted schema stays at 23. Coverage includes manual-cleared candidate filtering, direct command rejection, a fresh equal-amount source, next-statement clearing and restart, zero-net false reuse, period/recovery denial, legacy unlink/re-match/reconcile, preservation of original journal and reconciliation records, retained old source IDs, failure rollback, completed-line protection, categorisation reversal protection and auditor denial.

Full regression also exposed a pre-existing customer-return date bug: active credit allocations were compared using their audit creation timestamp instead of allocationDate. Return reversal chronology now uses the financial allocation date, retaining reversedAt as the actual undo cutoff for reversed allocations. Active allocations still block the owned return/credit reversal. A frozen-clock regression proves late data entry does not change this rule, that the return cannot be reversed before an allocation is actually undone, and that reversal succeeds after release.
