# Bank reconciliation completion and verified recovery

All bankReconciliations.complete callers now create a durable BANK_RECONCILIATION operation. The optional second argument supplies a stable operation ID; the desktop page preserves it across an uncertain submission and prevents overlapping clicks. Existing callers without an ID receive a generated ID. Result identity is bound before saving the completed reconciliation. A completed identical request returns its existing result; a changed payload or unacknowledged result cannot be replayed. Main command failure rolls back reconciliation records, clearing locks and operation metadata together. No schema change or external service is required.

The financial recovery workbench supports reconciliation results that already exist. The authenticated reviewer records evidence; another authorized account approves the current review revision. Main-process proof rechecks the saved intent, unique result identity, chronological prior reconciliations, cumulative clearing, current dated bank ledger, exact stored balances and differences, imported statement amounts and ledger matches. Missing/duplicated/reversed cleared rows, repeated clearing across periods, unresolved imports, mismatched intents or inconsistent totals remain blocked. Approval creates no GL entry and does not replay or change the completed reconciliation. Other unresolved operations retain their own blockers.

Restart diagnostics recognize reconciliation business results without demanding a nonexistent reconciliation GL journal. This count-based diagnostic is informational; full closure proof remains mandatory. PAYMENT_REVERSAL is a legacy reserved operation kind without a current producer and remains unsupported. Actual customer payment reversal uses the existing SALES_PAYMENT_REVERSAL procedure.

Automated acceptance covers stable retries and restart, changed request rejection, existing callers, invalid-request rollback, uncertain intent, independent actor identity, full financial record immutability, historical clearing, missing/duplicate results, wrong balances/date/cleared rows, reversed GL, imported statement mismatches, stale review revisions, read-only roles, failure rollback, corrupted storage and write/period-close gates.

Desktop acceptance used a disposable local profile. An independent FINANCE_ADMIN approved the saved BANK_RECONCILIATION result with reference NATIVE-RECON-APP-001. The unresolved count changed from 1 to 0 and closure history showed COMPLETED with distinct reviewer and approver identities. The real business profile was not used.
