# D06 阶梯返点与佣金后台 — 2026-11-01

仅 htt-backend。055 向前追加，不改 001—054。沿用 048 政策、claim、run、计提、结算、权限和财务核对表，不创建第二套激励账。没有配置真实合同、费率、银行付款或工资/STP；三个客户端不变。

## 本批范围

支持 NET_SALES、AUD 未税净销售额门槛，政策必须显式选择 WHOLE_AMOUNT（全额跳档）或 PROGRESSIVE（累进分段），以及 INVOICE 或 FIXED_WINDOW。没有隐含算法、费率或日历累计窗口。数量/基础单位阶梯、滚动窗口、回款和毛利口径未启用，不能用 JSON 自行绕过。原百分比、单票固定、基础单位固定政策保持原计算和 claim 钉住规则。

全额跳档：取不高于当前净额的最高门槛，对全部符合条件净额用该档费率。累进分段：每档仅计算该档下限至下一档下限之间的净额，最后一档无上限。门槛包含下限；零净额目标为零；全部计算使用 PostgreSQL numeric，最终金额四舍五入至 AUD 分，不按每档先舍入。

1–12 档，下限从 0 起严格递增；下限为非负 AUD、最多2位小数，最大999999999999.99；费率0–100、最多6位小数且不递减。允许零起步费率；不允许省略算法、重复/倒序门槛、额外档字段、字符串费率或混入旧 value 字段。

## 政策 API

复用 `/api/v1/incentives/programs/{programId}/policies`，请求中的 revision/from/to 及 config 原财务、结算、税务审核字段仍必需，仍须另一位当前有权限的成员批准。POST 写入均需 Idempotency-Key，有版本的资源需 If-Match；没有新增能绕过原审批的路径。

下列为合成演示，**不是推荐合同费率**。在原 config 内将 formula/value 换成：

```json
{
  "basis": "NET_SALES",
  "formula": "TIER_PERCENT_NET",
  "tierMode": "WHOLE_AMOUNT",
  "thresholdUnit": "AUD_NET",
  "window": "INVOICE",
  "tiers": [
    { "from": 0, "rate": 5 },
    { "from": 200, "rate": 10 }
  ]
}
```

其余如 expenseAccountId/liabilityAccountId/settlementMode/taxTreatment/taxReviewReference/deductRebates/retroactiveAcknowledged/recoverableGst 等按 C08 原契约提交。不能只提交上面片段。演示中净额300：全额跳档30；累进分段20；后续净额降至150，两种算法目标都变为7.50，差额反向计提。

## 固定累计窗口

配置 `window:"FIXED_WINDOW"`，并显式 `windowFrom:"2026-10-01"`、`windowTo:"2026-11-01"`（半开区间），长度1–366天。政策有效期及 review period 必须恰好等于该窗口。跨多月或不规则有限合同窗口可直接给定日期；不自动猜测财年/自然月/滚动周期。INVOICE 不接受 windowFrom/windowTo。

同 program 的固定窗口不能与任何已批准政策重叠；创建和独立批准均重查，防止两个提前建好的草稿并行批准后形成混合版本累计。固定窗口需新政策在新窗口生效，不追溯重写已批准窗口合同。单票政策仍保留原 claim 首次非零计提后钉住版本规则。

运行、批准重估、结算前检查会扩展至整个受益人窗口的已提交发票集合，不允许通过 invoiceIds 选子集改变档位。调用方传入的 invoiceIds 仍先验证公司/受益人/期间权限；扩展后最多50张发票，超出明确拒绝，不截断，也不允许分批把同一窗口当多个独立阶梯。被停用 program 仍按原规则停止新增未形成 claim 的来源，已有 claim 和追回继续处理。

每个政策窗口先算总目标，再按 eligibleNet 比例分配到发票。按发票 UUID 文本序累加权重，取“本次累计舍入金额−上次累计舍入金额”；因此每张发票为整数分，合计严格等于窗口总目标。分配顺序不代表发票获得边际档位，全部参与同一比例分摊。窗口低于门槛或退货/贷项降档会同时重新评估各发票权利。

冻结计划每行含 tierContract、windowEligibleNet、windowTarget、allocation，以及原来源事实、policyId/revision、priorAccrued、target/delta；审批重算整个同一窗口，新增发票、贷项或累计余额变化使旧 run 409。总权益的变化必须先独立批准，才能对窗口内任一 claim 结算或抵扣。窗口来源最大50票、每票事实/计划字节限制沿用 C08；生产规模性能需另验。

## 锁、财务与结算

公司激励锁→按UUID排序的完整窗口来源订单锁→原BAS/财务期间锁；批准、结算、抵扣使用完整窗口来源锁，阻止已有窗口来源的并发贷项穿过核对。快照代表当次已提交事实；后来提交的新发票或贷项在下一次重估中体现，结算前重查。不存在无限期冻结未来业务的承诺。

仍按“最新累计目标−已批准计提”过账差额，负差额反向过账；不修改历史分录。已锁 review period 的变化在后续开放财务期处理；关闭期保护、专属激励负债、完整来源凭证及总账延迟约束保持有效。既有草稿/basic合同不会因升级被隐含改成阶梯。

客户返点自己的已链接贷项仍排除于返点计算，避免自递归；普通数量/金额贷项及全额取消仍影响符合条件净额。税额单独调整不改变未税阶梯。CUSTOMER_CREDIT、SUPPLIER_BILL、CLEARING、OFFSET 沿用原合法单据、AR/AP、信用及现金/非现金 GST 规则。已结算后降档形成负权益并保留追回，不把清算/抵扣标为银行已付或已完成工资。D05 工资沙箱不自动消费佣金清算，更不会重复计工资费用。

沿用权限与公司/个人隔离；财务读取需 incentives/read、总账及完整客户权限。个人 API 仅显示本人/显式客户授权的批准汇总，不暴露阶梯合同、他人来源或科目。所有辅助计算、旧校验别名、窗口锁函数对 app/worker/portal 撤销直接执行权限。
