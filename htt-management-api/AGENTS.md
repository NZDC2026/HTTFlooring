# HTT Management API 工作规则

1. 使用 Java 21、Spring Boot 4.1.2、Maven Wrapper，根包 `com.htt.management`。依赖优先交由 Boot BOM 管理；额外版本必须说明兼容证据并验证。
2. 模块化单体，按业务模块组织。只创建有真实职责的类和目录；不生成空模块、无意义接口、通用 CRUD 基类或重复适配层。
3. 修改前阅读相关代码、测试及 `docs/adr`。保留用户已有改动；未授权不修改兄弟项目、不提交或推送 Git。
4. 以用户明确授权范围为准，已授权事项不重复询问。本项目已获准在 `192.168.10.174:5432` 创建 HTT 专用数据库、角色及业务所需表；不得修改其他系统。自动化测试只能使用本地 Testcontainers 或明确指定的 `htt_management_validation` 验证库，不能用 `htt_management` 主库试验迁移。服务变更、ERPNext 访问仍需相应授权。
5. 三端共享业务规则。客户端名称、角色字符串、公司请求头和本地演示会话都不能证明身份。所有数据读取和写入都需要已验证身份、权限和数据范围。
6. 正式订单只能由明确授权的管理人员创建。直接创建、报价转换、导入、定时任务等所有入口必须执行同一规则；客户和销售无此权限。
7. 财务与运营边界独立：订单不等于发票；开票不等于收入确认；退货、贷项、抵扣和退款分别建模。MYOB 未确认规则记录为 OPEN QUESTIONS，不自行补全。
8. 金额用 `BigDecimal` 和明确币种；对外金额契约优先十进制字符串。税率、单位、价格、地址等交易快照不得依赖可变主数据重新计算历史。
9. 事务由业务用例划定。数据库事务内不调用外部 HTTP/FCM/RabbitMQ；业务变更、幂等记录、审计及 Outbox 同事务提交。
10. 通知采用 PostgreSQL Outbox → RabbitMQ → notification 模块。FCM 与 SSE 是渠道；通知历史和恢复游标持久化。SSE 不是离线推送或消息队列。
11. Flyway 脚本一旦应用不可改写；禁止通过 Hibernate 自动修改业务表，禁止自动 baseline/clean。迁移必须有隔离数据库验证、核对及回滚方案。
12. 默认拒绝访问；健康检查不泄露细节。不得通过关闭鉴权、扩大全局 CORS 或在 URL 中传令牌来解决客户端接入问题。
13. 不提交密钥、真实客户数据或生产数据库导出。演示数据必须明确标识并与真实财务、库存、工资、通知隔离。
14. 对改动运行有意义的验证。普通验证：`./mvnw verify`；数据库验证：本地 Docker 下 `./mvnw -Ppostgres-it verify`，或加载 Validation 环境后 `./mvnw -Ppostgres-it -Dhtt.test.database=dedicated verify`。主库只执行已验证迁移及只读验收。明确区分通过、未执行、失败；不得静默跳过必需检查。
15. 交付说明实际修改、验证结果、剩余限制及下一阶段输入。架构决策记录状态和依据；不把规划写成已实现能力。
