# ADR-0003：通知可靠投递方向

日期：2026-11-05，2026-11-06 更新。状态：Outbox、消费、渠道任务、Fake Push、SSE 与恢复代码已实现；专用 PostgreSQL 和远程执行机上的真实 RabbitMQ 容器测试通过，FCM/APNs 真机未验证。实际边界和运行说明见 [通知模块](../notification.md)。

本轮复核：业务发布器的Bean配置已移至platform，通知关闭仍可提交Outbox；71项普通测试/JAR及7项真实PG/Rabbit容器测试通过。新增同链路真实HTTP/SSE、RSA验签、身份仓储/RLS、跨客户/门店隔离与游标恢复验证，测试取钥不连接实际IdP。文件/命令/回滚见 [验收记录](../plans/notification-verification.md)。

业务事务同时保存业务变更、审计及 Outbox。Publisher 用短事务领取有租约的记录，事务外发布到 RabbitMQ，收到 publisher confirm 并处理 mandatory return 后再标记成功。崩溃可能重发，因此承诺至少一次，不声称端到端恰好一次。

Notification Consumer 在同一数据库事务内通过唯一 eventId/inbox 去重，保存授权后的通知历史及渠道投递任务，提交后 ACK。后续 FCM 网络投递不占业务事务；瞬时错误有上限指数退避和抖动，永久错误停用失效 token，耗尽重试进死信并保留审计重放入口。网络超时后的发送结果可能未知，客户端按通知 ID 去重。

SSE 只负责在线提醒。历史、已读状态和恢复游标存 PostgreSQL；连接与回放重新校验用户和公司范围，撤权时关闭连接。游标必须保证提交顺序不漏读，不能直接假定普通序列分配顺序就是事务提交顺序。设置心跳、每用户连接上限、写缓冲上限及过慢客户端断开策略，不能每条 SSE 连接长期占用一个数据库连接。

多个 API 实例需要把唤醒信号送到持有用户连接的实例，并由数据库补读；不能用一个竞争消费者队列替代跨实例通知。Publisher、Consumer 和 API 可以从同一产物按角色部署，初始并发和批量通过本地压测确定。

iOS 经 FCM 仍需正确配置 APNs。当前未确认 Firebase 项目和 APNs 密钥，不建立虚假配置。事件内容只携带必要标识，避免把敏感财务明细推到锁屏。通知偏好、历史保留期、通知模板和部署资源待确认。
