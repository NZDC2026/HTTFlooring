# ADR-0002：业务所有权与正式订单权限

日期：2026-11-05。状态：约束已采用；业务实现和未确认财务规则待后续阶段。

## 决定

采用模块化单体和轻量 DDD。三端复用同一业务规则，模块用例负责事务，控制器处理协议。模块间调用明确用例或发布事件，不直接写入其他模块拥有的数据表。需要强一致时在同一 PostgreSQL 事务中协作，避免无意义分布式事务。

| 模块 | 数据所有权 | 主要允许依赖 |
| --- | --- | --- |
| identity | 已验证身份、成员关系、权限与数据范围 | platform |
| crm | 客户、供应商、分支、联系人、业务活动 | identity |
| catalog / pricing | 产品、单位；价格及规则 | crm、identity；pricing → catalog |
| sales | 报价、正式订单和交易快照 | crm、catalog、pricing、identity |
| inventory / fulfilment | 库存流水；拣货、交付与履约凭证 | catalog、identity；fulfilment → sales、inventory |
| purchasing | 采购承诺与收货流程 | crm、catalog、inventory、identity |
| finance | 发票、应收、贷项、分配、付款等已确认财务行为 | 明确的主数据契约和业务事件 |
| notification | 通知历史、偏好、设备、投递状态与游标 | identity、platform；不依赖运营内部实现 |
| document / reporting | 文件及访问元数据；授权读模型 | identity、明确的业务访问契约 |
| platform | HTTP、安全接线、审计/Outbox 基础设施 | 不依赖具体业务模块 |

此表是方向，不创建对应空目录。finance 不把销售订单对象当发票；运营模块不能直接写财务账。总账、BAS、银行对账和工资范围未确认，暂不实施。

所有正式订单创建途径都要求：已验证身份、有效公司成员关系、明确管理授权、`sales.orders.create` 权限，以及客户/分支/仓库等数据范围。客户和销售不得创建正式订单。报价转换、导入或管理端来源不能绕过规则；不自动将旧系统 ADMIN/OFFICE/ACCOUNTANT 等角色映射成订单授权。

公司/客户/仓库 ID 是选择条件，不是权限证明。列表、详情、搜索、聚合、附件、导出、通知历史及 SSE 均受相同范围约束。身份提供方和完整范围矩阵未确认前保持默认拒绝。

## 已观察到的冲突与后果

- 客户门户主要为本地演示，退货确认和贷项应用按钮不能视为客户正式权限依据。
- Flutter 有本地演示身份、报价转发票流程；不得照搬到正式身份和开票权限。
- 旧后端的直接订单创建与报价审批转换使用不同权限；新实现需要统一守卫。
- 贷项签发是否立即减少原发票应收，各端语义不一致；在确认前不得迁移余额计算逻辑。

必须由后续需求和契约测试确认这些差异。第一阶段没有移植任何业务流程。
